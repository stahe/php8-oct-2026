    7. Les exceptions et erreurs

    Lorsqu'une méthode d'une classe rencontre une erreur irrécupérable (fichier inexistant, base de données non connectée, connexion réseau hors service), elle n'affiche pas une erreur sur une console (fichier, base de données) mais lance une exception. Les exceptions étendent la classe [\Exception]. Outre des exceptions, le fonctionnement interne de PHP lance également des erreurs dont la classe de base est la classe [\Error]. Les deux classes implémentent l'interface PHP [\Throwable].

    PHP 8 a profondément changé la gestion des erreurs : de nombreuses situations qui produisaient en PHP 7 un simple avertissement (et un résultat souvent absurde) lancent désormais une erreur que l'on peut intercepter. Nous le verrons au fil des exemples.

    L'interface [\Throwable] est la suivante (cf. documentation) :

    interface Throwable extends Stringable
{
    public function getMessage(): string;
    public function getCode(): int;
    public function getFile(): string;
    public function getLine(): int;
    public function getTrace(): array;
    public function getTraceAsString(): string;
    public function getPrevious(): ?Throwable;
    public function __toString(): string;
}

    Le rôle des méthodes de l'interface est le suivant :

    Méthode
    Rôle
    [getMessage]
    rend le message d'erreur
    [getCode]
    rend le code de l'erreur (un entier)
    [getFile]
    rend le nom du fichier où l'objet a été créé
    [getLine]
    rend le numéro de la ligne où l'objet a été créé
    [getTrace]
    rend la pile des appels de fonctions sous la forme d'un tableau
    [getTraceAsString]
    rend la pile des appels de fonctions sous la forme d'une chaîne de caractères
    [getPrevious]
    rend l'objet [Throwable] précédent (encapsulé), ou [null]
    [__toString]
    rend une représentation de l'objet sous forme de chaîne de caractères

    On remarquera que l'interface [Throwable] étend l'interface [Stringable] rencontrée au chapitre sur les classes. Une classe ne peut pas implémenter directement l'interface [Throwable] : elle doit dériver de [\Exception] ou de [\Error].

    7.3. Les exceptions et erreurs prédéfinies dans PHP 8

    Le script [throwables.php] suivant affiche l'arborescence des classes prédéfinies qui implémentent l'interface [Throwable]. Nous l'utilisons pour obtenir une liste exacte, celle de PHP 8.5, plutôt que de la recopier d'une documentation. Le lecteur ne perdra rien s'il ne cherche pas à comprendre son code, qui utilise l'API de réflexion de PHP (la classe [ReflectionClass] permet d'interroger PHP sur une classe : son nom, son extension d'origine, ses interfaces...) et une fonction récursive :

    <?php

// respect strict des types déclarés des paramètres de fonctions
declare(strict_types=1);

// affiche l'arborescence des classes prédéfinies implémentant l'interface [Throwable]
// on se limite aux extensions toujours présentes dans PHP 8.5 :
// le noyau (Core), la bibliothèque standard, la bibliothèque SPL, jSON et Random
$extensions = ["Core", "standard", "SPL", "json", "random"];

// les classes prédéfinies de ces extensions qui implémentent [Throwable]
$classes = array_filter(
    get_declared_classes(),
    function (string $classe) use ($extensions): bool {
        $reflexion = new ReflectionClass($classe);
        return $reflexion->isInternal()
            && $reflexion->implementsInterface(Throwable::class)
            && in_array($reflexion->getExtensionName(), $extensions, true);
    }
);
sort($classes);

// affichage récursif des classes filles de la classe [$parent]
function afficher(?string $parent, array $classes, string $indentation): void
{
    // les filles directes de [$parent]
    $filles = array_values(array_filter(
        $classes,
        fn(string $classe): bool => (get_parent_class($classe) ?: null) === $parent
    ));
    foreach ($filles as $i => $fille) {
        $derniere = $i === count($filles) - 1;
        print $indentation . ($derniere ? "└── " : "├── ") . $fille . "\n";
        afficher($fille, $classes, $indentation . ($derniere ? "    " : "│   "));
    }
}

print "Throwable\n";
afficher(null, $classes, "");

    Commentaires

    • ligne 13 : la fonction [get_declared_classes] rend la liste de toutes les classes connues à cet instant, prédéfinies ou non ;
    • lignes 16-18 : on ne garde que les classes prédéfinies (internal), qui implémentent l'interface [Throwable] et qui appartiennent aux extensions toujours présentes dans PHP 8.5 (ligne 9). D'autres extensions ajoutent leurs propres exceptions (par exemple [PDOException] pour l'accès aux bases de données, que nous rencontrerons plus tard) ;
    • lignes 24-36 : une fonction récursive qui affiche les classes filles directes de la classe [$parent], puis les filles de chacune d'elles, etc. La fonction [get_parent_class] rend [false] pour une classe sans parent : l'opérateur [?:] transforme alors [false] en [null] ;
    • ligne 29 : une fonction fléchée (arrow function, PHP 7.4), forme courte d'une fonction anonyme réduite à une expression ;
    • ligne 39 : on part des classes sans parent : [Error] et [Exception].

    Les résultats montrent deux familles :

    • la famille [Exception] : ce sont les exceptions que lancent les bibliothèques et le code applicatif. On y trouve :
      • [ErrorException], qui permet de transformer un avertissement de PHP en exception (nous l'utiliserons en fin de chapitre) ;
      • [JsonException] (PHP 7.3), lancée par [json_encode] et [json_decode] avec l'option [JSON_THROW_ON_ERROR] ;
      • [Random\RandomException] (PHP 8.2), lancée par les fonctions de génération de nombres aléatoires ;
      • les exceptions de la bibliothèque SPL (Standard PHP Library), une collection de classes et d'interfaces destinées à résoudre des problèmes rencontrés fréquemment par les développeurs. Elles forment deux sous-familles :
      • [LogicException] et ses dérivées : des erreurs de programmation, qu'une correction du code doit faire disparaître : argument invalide ([InvalidArgumentException]), valeur hors du domaine attendu ([DomainException]), méthode inexistante ([BadMethodCallException])... ;
      • [RuntimeException] et ses dérivées : des erreurs qui ne peuvent être détectées qu'à l'exécution : indice hors bornes ([OutOfBoundsException]), valeur inattendue ([UnexpectedValueException]), dépassement de capacité ([OverflowException])... ;
    • la famille [Error] : ce sont les erreurs lancées par le moteur de PHP lui-même. On y trouve :
      • [TypeError] : une valeur n'a pas le type attendu (paramètre de fonction, attribut typé, valeur de retour, opérande d'un opérateur...). Sa dérivée [ArgumentCountError] signale un nombre d'arguments insuffisant ;
      • [ValueError] (PHP 8.0) : une valeur a le bon type mais une valeur invalide (par exemple une longueur négative ou nulle) ;
      • [ArithmeticError] et sa dérivée [DivisionByZeroError] : erreurs dans les opérations arithmétiques ;
      • [UnhandledMatchError] (PHP 8.0) : aucune branche d'une expression [match] ne convient ;
      • [AssertionError] : échec d'une assertion [assert] ;
      • [CompileError] et sa dérivée [ParseError] : erreur de syntaxe dans un fichier chargé par [require] ou [include] ;
      • [FiberError] (PHP 8.1) et [Random\RandomError] (PHP 8.2) : erreurs liées aux fibres et aux générateurs aléatoires, que nous n'utiliserons pas .

    Les deux familles n'ont aucun lien de parenté : une clause [catch (\Exception $e)] n'intercepte pas une erreur [Error]. Seule l'interface [Throwable] les réunit.

    Commentaires

    • ligne 7 : on demande à PHP de signaler toutes les erreurs. Le paramètre de la fonction [error_reporting] est le niveau d'erreurs signalées. C'est une combinaison des constantes suivantes (les principales) :
    Constante
    Signification
    [E_ERROR]
    erreur fatale à l'exécution : le script est arrêté
    [E_WARNING]
    avertissement : le script continue
    [E_PARSE]
    erreur de syntaxe détectée à la compilation
    [E_NOTICE]
    remarque : quelque chose qui pourrait être une erreur
    [E_DEPRECATED]
    utilisation d'une fonctionnalité dépréciée, qui disparaîtra dans une version future
    [E_USER_WARNING], [E_USER_NOTICE], [E_USER_DEPRECATED]
    les mêmes niveaux, déclenchés par le code avec la fonction [trigger_error]
    [E_ALL]

    • ligne 12 : on accède à un élément inexistant du tableau [$var] ;
    • ligne 14 : on fait une division par zéro ;
    • ligne 17 : on crée une instance de la classe [SplFixedArray] de la bibliothèque SPL. Cette classe permet de créer un tableau à bornes fixes et à indices entiers ;
    • ligne 21 : on accède à un élément inexistant du tableau.

    <?php

// respect strict des types déclarés des paramètres de fonctions
declare(strict_types=1);

// on affiche toutes les erreurs
error_reporting(E_ALL);
ini_set("display_errors", "1");
// on entoure le code par un try / catch
try {
    $var = [];
    // clé inconnue
    print $var["abcd"];
    // division par zéro
    $var = 7 / 0;
    var_dump($var);
    // tableau à bornes fixes
    $array = new \SplFixedArray(5);
    $array[1] = 2;
    $array[4] = "foo";
    // indice en-dehors des bornes
    $array[5] = 8;
    // vérification
    print "ce message ne sera pas affiché\n";
} catch (\Throwable $ex) {
    // \Throwable est l'interface implémentée par toutes les erreurs et exceptions
    // on affiche l'exception
    print "erreur, message : " . $ex->getMessage() . ", type : " . $ex::class . "\n";
}

    Commentaires

    • le script est celui qui a été présenté au paragraphe précédent. Seulement maintenant on a entouré le code susceptible de provoquer des erreurs par une structure [try / catch] : si le code des lignes 11-24 provoque (lance) une exception ou une erreur, celle-ci sera gérée par la clause [catch] des lignes 25-29 ;
    • ligne 25 : le paramètre de la clause [catch] est le type d'exception ou d'erreur que l'on veut gérer. En mettant comme type [\Throwable] qui est une interface, on indique qu'on veut gérer toute instance de classe implémentant l'interface [\Throwable]. Comme toutes les classes d'erreurs et d'exceptions implémentent cette interface, la clause [catch] gère ici toute erreur / exception ;
    • ligne 15 : l'instruction qui déclenche l'erreur. Dès qu'il y a exception, il y a branchement sur la clause [catch]. Le code qui suit dans le [try] n'est donc pas exécuté ;
    • ligne 28 : la notation [$ex::class] rend le nom de la classe de l'objet [$ex].

try {
    // indice en-dehors des bornes

} catch (\RuntimeException $ex) {
    // affichage message d'erreur
    print "Erreur 3 : " . $ex->getMessage() . "\n";

    // indice en-dehors des bornes
    $array[5] = 8;

try {

    // affichage message d'erreur

try {

    • lignes 11-41 : 4 façons différentes de gérer l'exception générée par l'utilisation d'un indice incorrect avec la classe [\SplFixedArray]. Le changement n'a pas cassé le code existant puisque la classe [OutOfBoundsException] dérive de la classe [RuntimeException] ;
      • ligne 15 : gère une erreur de type [\Throwable]. C'est valide puisque le type [OutOfBoundsException] dérive du type [\Exception] qui implémente l'interface [\Throwable] ;
      • ligne 23 : gère une erreur de type [\Exception]. C'est valide puisque le type [OutOfBoundsException] dérive du type [\Exception] ;
      • ligne 31 : gère une erreur de type [\RuntimeException]. C'est valide puisque le type [OutOfBoundsException] dérive du type [\RuntimeException]. C'est un bon choix : le code fonctionne quelle que soit la version de PHP ;
      • ligne 39 : gère le type exact de l'exception générée ;
    • lignes 46-81 : 5 façons différentes de gérer l'erreur générée par la fonction [intdiv] lorsqu'on passe à celle-ci un diviseur égal à 0.       • ligne 55 : on intercepte le type exact de l'erreur : c'est la méthode à privilégier ;
      • ligne 63 : on intercepte le type [\ArithmeticError]. C'est valide puisque la classe [DivisionByZeroError] étend la classe [ArithmeticError] ;
      • ligne 71 : on intercepte le type [\Error]. C'est valide puisque la classe [DivisionByZeroError] dérive de la classe [Error] ;
      • ligne 79 : on intercepte le type [\Exception]. C'est invalide car la classe [DivisionByZeroError] n'a aucun lien avec la classe [\Exception] .

    7.7. Clause [finally]

    La structure [try / catch] peut avoir un troisième élément et devenir une structure [try / catch / finally]. Le code de la clause [finally] est exécuté dans les deux cas suivants :

    • la clause [try] ne lance pas d'exception. Elle est alors exécutée entièrement puis l'exécution du code passe à la clause [finally] qui est exécutée entièrement ;
    • la clause [try] lance une exception. Elle est alors exécutée jusqu'à l'instruction qui lance l'exception. L'exécution du code passe alors à la clause [catch] qui est exécutée entièrement. Puis l'exécution du code passe à la clause [finally] qui est exécutée entièrement .

    Finalement, le code de la clause [finally] est toujours exécuté. Ce scénario est utile dans le cas suivant :

    • dans le [try], le code a obtenu des ressources (fichiers, bases de données, connexions réseau, files d'attente). En général ces ressources sont coûteuses. Il faut alors les rendre (on dit le plus souvent fermer) dès que c'est possible ;
    • si l'acquisition des ressources a été faite dans le [try], on mettra leur restitution dans le [finally]. Cela nous assure que dans tous les cas (erreur ou pas), les ressources acquises sont restituées au système .

function lireAge(array $data): int
{
    $age = $data["age"] ?? throw new \InvalidArgumentException("L'âge est absent");
    return is_int($age) && $age >= 0 ? $age : throw new \DomainException("Âge [$age] invalide");
}

// une fonction fléchée qui ne fait que lancer une exception
$interdit = fn(string $operation) => throw new \LogicException("Opération [$operation] interdite");

// des données de test
$tests = [["age" => 48], [], ["age" => -4]];
foreach ($tests as $i => $data) {
    try {
        print "test $i : âge=" . lireAge($data) . "\n";
    } catch (\InvalidArgumentException | \DomainException $ex) {
        // une seule clause [catch] pour deux types d'exceptions
        print "test $i : " . $ex::class . " : " . $ex->getMessage() . "\n";
    }
}

try {
    $interdit("suppression");
} catch (\LogicException) {
    // depuis PHP 8.0, la variable de la clause [catch] est facultative
    print "l'opération a été refusée\n";
}

// encapsuler une exception de bas niveau dans une exception de l'application
class DaoException extends \RuntimeException
{
}

function lireConfiguration(string $json): array
{
    try {
        return json_decode($json, true, flags: JSON_THROW_ON_ERROR);
    } catch (\JsonException $ex) {
        // la cause originelle est passée en 3e paramètre : elle n'est pas perdue
        throw new DaoException("Configuration illisible", 10, $ex);
    }
}

try {
    lireConfiguration('{"dsn": "mysql:host=localhost"');
} catch (DaoException $ex) {
    print $ex::class . " : " . $ex->getMessage() . " (code " . $ex->getCode() . ")\n";
    print "cause : " . $ex->getPrevious()::class . " : " . $ex->getPrevious()->getMessage() . "\n";
}

    Commentaires

    • ligne 9 : depuis PHP 8.0, [throw] est une expression et non plus seulement une instruction. On peut donc l'utiliser là où une valeur est attendue : ici, après l'opérateur [??]. Si la clé [age] n'existe pas, l'exception est lancée ; sinon [$age] reçoit sa valeur ;
    • ligne 10 : [throw] utilisé dans une expression conditionnelle [? :] ;
    • ligne 14 : une fonction fléchée dont le corps se réduit à lancer une exception. Avant PHP 8.0, c'était impossible : une fonction fléchée ne peut contenir qu'une expression ;
    • ligne 21 : une seule clause [catch] pour deux types d'exceptions (lignes 3-4 des résultats). On remarquera que [InvalidArgumentException] et [DomainException] dérivent toutes deux de [LogicException] : un [catch (\LogicException $ex)] aurait eu le même effet ;
    • ligne 29 : depuis PHP 8.0, la variable de la clause [catch] est facultative lorsqu'on n'a pas besoin de l'exception, seulement de son type (ligne 5) ;
    • lignes 35-37 : une exception propre à l'application. Dans les chapitres suivants, nous écrirons des couches d'accès aux données (DAO, Data Access Object) qui ne lanceront que ce type d'exception, quelle que soit l'origine de l'erreur (fichier, jSON, base de données) ;
    • lignes 39-47 : la fonction [lireConfiguration] décode une chaîne jSON. L'exception de bas niveau [JsonException] est interceptée et encapsulée (ligne 45) dans une exception [DaoException]. La cause originelle est passée en 3e paramètre du constructeur ;
    • ligne 53 : le code appelant ne connaît que [DaoException], mais il peut retrouver la cause originelle de l'erreur avec la méthode [getPrevious] (lignes 6-7 des résultats).

    7.13. Transformer les avertissements en exceptions : [ErrorException]

    Malgré les progrès de PHP 8, certaines anomalies restent de simples avertissements : clé de tableau inexistante, variable non définie, fichier impossible à ouvrir avec [fopen]... Ces avertissements ne peuvent être interceptés par un [try / catch]. On peut cependant installer un gestionnaire d'erreurs qui les transforme en exceptions [ErrorException]. C'est ce que fait le script [exceptions-11.php] :

// respect strict des types déclarés des paramètres de fonctions
declare(strict_types=1);

// gestionnaire d'erreurs : transforme les avertissements de PHP en exceptions [ErrorException]
set_error_handler(function (int $niveau, string $message, string $fichier, int $ligne): bool {
    throw new \ErrorException($message, 0, $niveau, $fichier, $ligne);
});

// une clé inconnue ne provoque plus un simple avertissement mais une exception
$personne = ["nom" => "Langevin"];
try {
    print $personne["prenom"] . "\n";
} catch (\ErrorException $ex) {
    print "Erreur : " . $ex->getMessage() . " (ligne " . $ex->getLine() . ")\n";
    print "niveau E_WARNING : " . var_export($ex->getSeverity() === E_WARNING, true) . "\n";
}
// idem pour l'ouverture d'un fichier inexistant
try {
    $flux = fopen(__DIR__ . "/inexistant.txt", "r");
} catch (\ErrorException $ex) {
    print "Erreur : " . $ex->getMessage() . "\n";
}
// on revient au gestionnaire d'erreurs de PHP
restore_error_handler();
print "fin\n";

    Commentaires

    • lignes 7-9 : la fonction [set_error_handler] installe un gestionnaire d'erreurs : une fonction que PHP appellera à chaque avertissement, remarque ou dépréciation, au lieu d'afficher son message. Elle reçoit le niveau de l'erreur, son message, le fichier et la ligne où elle s'est produite. Ici, elle lance une exception [ErrorException] qui mémorise ces informations. Le type de retour [bool] est celui que prévoit la documentation de [set_error_handler] : la fonction rendrait [false] pour laisser PHP traiter l'erreur normalement. Elle ne rend jamais rien ici puisqu'elle lance toujours une exception ;
    • ligne 14 : la clé [prenom] n'existe pas. Au lieu d'un avertissement, on obtient une exception [ErrorException] que l'on intercepte (ligne 2 des résultats) ;
    • ligne 17 : la méthode [getSeverity], propre à la classe [ErrorException], rend le niveau de l'erreur d'origine (ligne 3) ;
    • ligne 21 : l'ouverture d'un fichier inexistant devient également une exception (ligne 4) ;
    • ligne 26 : rétablit le gestionnaire d'erreurs précédent, ici celui de PHP.

    Cette technique est utilisée par de nombreux frameworks PHP (Symfony, Laravel) : en développement, tout avertissement devient une exception, ce qui oblige à corriger le code. L'outil de tests [PHPUnit] que nous utiliserons plus loin procède de façon analogue : il peut faire échouer un test qui produit un avertissement ou une dépréciation.
